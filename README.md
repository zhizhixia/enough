# 🧭 Enough —— 够用就好（enough）

> 模型已经足够强大，轮子已经足够丰富，缺的只是一个恰到好处的引导。

[English](README.en.md) | [中文](README.md)

Enough 是一个给 AI 编程助手（Codex、Claude Code、OpenCode 等）用的 Skill：它用风险分级、复用优先和证据驱动的方式，帮助手把软件任务推进到“够用且能交付”，而不是想到哪写到哪，也不是把每件小事变成重流程。

## 为什么要做这个东西？

如果你经常让 AI 帮你写功能，大概率遇到过下面这些情况：

**1. 白干一场**
AI 兴致勃勃写了一堆代码，后来才发现已有项目或现有模块已经能解决问题。

**2. 方向错了才发现**
AI 没问清真正影响范围的约束就动手，做到一半才发现方向不对。

**3. 什么都做，什么都不通**
AI 同时铺开十个模块；最后集成时，主流程根本跑不通。

**4. “构建成功”不等于“能用”**
AI 说“测试全过了”，其实只有编译或 Mock 成功，真实路径一跑就崩。

**5. 发布事故**
密钥写进代码、临时文件混进仓库、调试配置没关——上线后才发现。

**6. 同一个问题修不好**
AI 反复猜同一个 bug，改一次崩一次，却没有停下来判断根因。

**7. 流程太重**
改个错字也被要求调研、设计、全套回归；时间花在仪式上，不在结果上。

**8. 为测而测**
为了“覆盖率”或“必须 TDD”新增脆弱测试，却没有证明真实风险。

Enough 把靠谱工程师的判断写成 AI 能执行的流程：该停时停、该做时做，证据够了就结束。

## 核心理念

模型的能力已经足够，开源和现有项目里的能力也已经足够。Enough 不教 AI 怎么写每一行代码；它只在容易翻车的节点提醒 AI：**先看已有能力，按风险选路径，只在必要时设计和搜索，用相称证据验收。**

| 关键问题 | Enough 的默认答案 |
| --- | --- |
| 先找什么？ | 先查当前项目的模块、依赖、接口、测试和既有决策 |
| 什么时候外部搜索？ | 只有新项目、重要依赖/能力选型，或“采用还是自建”确实需要比较时 |
| 什么时候批准设计？ | 复杂功能、新项目、重要模型/契约或安全与数据边界变化时 |
| 如何验证？ | 先判断需要证明什么、现有证据够不够、是否值得永久测试，再单独决定是否 TDD |
| 什么时候停止？ | 已批准验收项有充分证据、没有阻断问题且限制已披露时 |

## 它是怎么工作的？

### 先按风险分三档

不是所有任务都走同一套步骤。Enough 会根据失败影响、波及范围、可逆性、不确定性和外部状态影响选择路径；文件类型或任务长度不能单独定级。

| 档位 | 适用任务 | 会做什么 | 默认不做什么 |
| --- | --- | --- | --- |
| 🐇 **FAST** | 局部、低影响、可逆且验收明确的修改 | 看改动范围与上下文，实施，运行最近的原生检查或必要冒烟 | 外部选型、正式设计、永久新测试、完整审查链 |
| 🏗️ **NORMAL** | 边界明确、风险可控的普通功能或修复 | 写出简短验收和可信失败模式，复用现有证据，完成受影响的真实路径，再独立验收 | 默认严格 TDD、逐函数测试、固定双审、全量回归 |
| 🚨 **DEEP** | 高影响、难恢复、关键契约不确定，或涉及并发、认证/隐私、迁移、外部状态 | 针对具体风险补强设计、异常证据、受控环境和恢复措施 | 未授权真实操作，或机械开启所有“高级流程” |

### 复用优先，但不为搜索而搜索

1. **先查已有能力。** 能在当前项目复用的模块、接口、依赖、测试或既有结论，先直接复用。
2. **真正选型才外部搜索。** 新项目、重要新依赖、新自建能力，或成熟方案与自建之间确有取舍时，才做 GitHub 复用决策；结论可以是直接使用、使用并扩展、只借鉴或自建。
3. **常规任务不被搜索卡住。** 文案、小修复和已有实现的局部扩展不因 GitHub 不可用而阻塞。真正选型的搜索不完整时，如实说明限制，不把它伪装成已验证的自建结论。

### 设计、实现与验收按需要发生

复杂任务先明确目标、非目标、验收、边界和失败行为，并取得批准；小而明确的任务在对话里确认目标和验收即可。存在真实跨边界系统时，先验证最小纵向闭环；小任务不硬造“全系统路径”。

主代理始终负责风险、授权、接口一致性、整合和验收，不能把子代理的“完成”当成交付。委派或跨角色协作时，子代理继承既定策略；主代理仍要独立检查产物并运行选定验证。

### 测试不是一道固定门

Enough 把三个问题分开判断：

1. **已有证据够吗？** 用测试、类型/静态检查、构建、启动或真实场景证明可观察结果、不变项和可信失败模式；够用就不新增测试。
2. **值得新增永久测试吗？** 只有可重复真实风险、稳定观察边界、独立预期和持续回归价值同时存在时才新增；否则用临时诊断、冒烟、集成运行或可重复人工步骤。
3. **要测试先行吗？** 只有用户要求，或契约清楚、反例稳定且 TDD 确有约束收益时，才在指定边界采用。实现后补的独立行为测试同样有效。

Mock、自动测试、构建成功和真实环境验证是不同强度的证据，不能互相冒充。

### 高风险不是自动执行权

外部写入、安全、隐私、资金、部署、账号、生产数据和工业设备属于 DEEP。Enough 会要求明确目标、授权、不可逆影响和补救，并按风险选择最小权限、Dry Run、状态查询、受控 Canary、恢复方案和异常验证；这不等于获得真实调用、发布或部署的授权。

## 解决了什么问题？（对照表）

| 你遇到的痛点 | Enough 怎么解决 | 对应机制 |
| --- | --- | --- |
| 白干一场 | 先查现有能力；真正选型时再比较成熟方案与自建 | 复用优先 |
| 方向错了才发现 | 只把真正改变范围的复杂决策拿来批准 | 按需设计 |
| 什么都做、什么都不通 | 有真实跨边界时先证明最小纵向闭环 | 核心契约与集成优先 |
| 假测试、假完成 | 分清 Mock、测试、构建与真实运行；逐项验收 | 证据驱动 |
| 发布事故 | DEEP 按具体风险采用受控验证与恢复措施 | 风险相称的保护 |
| 同一个 bug 修不好 | 同一路径连续失败两次后先分类根因 | 停止猜测 |
| 流程太重 | FAST 直接做；NORMAL 和 DEEP 只做相称动作 | FAST / NORMAL / DEEP |
| 为测而测 | 永久测试和 TDD 都是独立、按价值作出的决定 | 三个验证判断 |

## 真实案例：它帮使用者避开了什么

**案例：想做一个 RSS 阅读器，结果一行代码都没写。**
当需求是 Windows 本地 RSS 阅读器、多源订阅、关键词过滤、定时刷新和一键安装时，这属于真正的产品选型。Enough 的复用决策发现 RSS Guard 已覆盖核心需求，于是推荐先试用成熟项目，而不是为了“写代码”自建。详见 [RSS Guard 复用决策](examples/reuse-decision-rss-guard.md)。

另一个脱敏案例中，“进阶日记”在确定原生 Android、本地存储和系统身份认证后，复用结论从“扩展现成项目”变为“只借鉴数据模型、原生自建”。随后才用最小闭环和里程碑交付，并把迁移测试和文档写入缺口明确留在验收对账里，见 [Mind Journal 端到端案例](examples/mind-journal-end-to-end.md)。

更多输入 → 输出示例见 [examples/](examples/)。其中标注为 v0.1 的材料只保留历史过程，当前行为以本页和 `skills/enough/SKILL.md` 为准。

## 快速开始

**一键安装（GitHub 官方 CLI）**：

```bash
gh skill install zhizhixia/enough enough --agent codex --scope user
```

**通用安装器（skills.sh）**：

```bash
npx skills add zhizhixia/enough --yes
```

**手动安装（零依赖）**：把 `skills/enough/` 文件夹拷贝到客户端的 skills 目录；保留 `SKILL.md`、`references/` 和 `agents/`。例如 Codex 可使用 `~/.codex/skills/enough/`。随后按客户端要求重启或刷新技能列表。

> 独立仓库提供 Enough 的核心流程和随附参考资料；它**不会**自动安装 Hermes 的全局自然语言自动路由规则，也不会自动带来 brainstorming、verification-planning、CodeGraph 等配套 Skill。客户端对自动触发的支持也不同：自动路由可用时自然描述软件任务即可；需要明确调用时，使用 `使用 $enough 按风险分级、复用优先和证据驱动推进：<任务>`，或使用该客户端等价的显式 Skill 调用语法。

可选配套能力缺失时，Enough 使用等价的简化步骤，不中断任务。

## 适合谁？

- 用 AI 辅助写代码，但希望 AI “靠谱一点”的开发者。
- 维护现有项目，不想因为每个需求都重新造轮子的人。
- 项目涉及真实账号、真实数据、迁移或外部状态，不能接受“差不多就行”的人。
- 刚接触 AI 编程，又不想把每个小改动变成重型流程的新手。

## 和其他方法论相比

Enough 的定位是“按风险够用的流程引导”，不是预设关卡或全套项目管理框架。

| 维度 | **Enough** | Superpowers | OpenSpec / Spec Kit |
| --- | --- | --- | --- |
| 定位 | 风险分级、复用与证据决策 | 完整方法论 + 技能体系 | 规格驱动的开发框架 |
| 轻任务处理 | FAST 只做最近的必要检查 | 取决于安装的工作流 | 通常仍需规格流程 |
| 外部搜索 | 只在真正选型时做 | 取决于具体工作流 | 非核心能力 |
| 设计批准 | 只用于复杂设计或关键边界 | 取决于具体工作流 | 以规格为中心 |
| 测试 | 证据、永久测试、TDD 分开判断 | 取决于具体工作流 | 取决于项目约定 |
| 依赖 | 纯 Markdown；可独立使用 | 依赖对应工具的技能体系 | 需要 CLI 与规格目录 |
| 自动触发 | 由宿主客户端和安装方式决定 | 由宿主工具决定 | 由 CLI 命令驱动 |

**什么时候选 Enough**：个人或小团队、多客户端环境，想让 AI 先判断风险和已有能力，再用足够的证据完成任务。

**什么时候选它们**：需要团队级规格管理与跨仓库协作时，选 OpenSpec / Spec Kit；想要完整方法论全家桶时，选 Superpowers。它们不冲突；Enough 可与已有能力协作，但不自动安装其余生态。
