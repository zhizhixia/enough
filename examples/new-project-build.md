# 示例：新项目自建——候选全部验证后的结论

> **v0.1 历史材料。** 保留一次新项目选型和纵向闭环的完整过程。v0.2 只在真正选型时外部搜索，不要求固定候选数量；纵向闭环仅适用于真实跨边界系统，不是所有任务的固定步骤。

## 输入（用户请求）

"做一个 Windows 本地新闻聚合应用：多源订阅、跨源去重、AI 摘要、关键词过滤、定时更新、一键启动。"

## Enough 的输出（简化自真实运行）

### 复用决策

- 目标：Windows 本地优先的新闻聚合应用，含 AI 摘要与跨源去重
- 搜索范围：GitHub 仓库搜索（产品场景、核心功能+技术栈、中文同义词与 Awesome 列表），初筛约 40 个候选，深入核验 5 个
- 搜索限制：均未本机安装运行，证据等级为 E2

| 候选 | 核心匹配 | 关键缺口 | 结论 |
| --- | --- | --- | --- |
| Fluent Reader | 多源、过滤、Windows | 无 AI 摘要、无跨源去重 | 不采用 |
| RSS Guard | 多源、过滤、定时、Windows | 无 AI 摘要 | 不采用 |
| Miniflux | 多源、过滤、定时 | 需 PostgreSQL；Web 形态；无摘要 | 不采用 |
| Folo | 多源、AI 摘要 | 依赖云账号，非本地优先；AGPL | 不采用 |

- 推荐：**自建（轻量 Python 应用）**
- 理由：需求组合（本地优先 + AI 摘要 + 跨源去重）无单一候选完整覆盖；扩展现有候选需要在大型代码库上重写核心逻辑，总拥有成本高于自建
- 借鉴点：Fluent Reader 的规则引擎思路、Miniflux 的条件请求（ETag/Last-Modified）与正则过滤
- 下一步：确认自建方向后，先定义最小纵向闭环，再进入设计

### 最小纵向闭环（定义）

`订阅源 → 定时抓取 → 解析 → 去重入库 → 过滤/摘要 → UI 展示`

这条路径通过前不扩大并行；用真实订阅源验证，Mock 成功不能替代。

### 阻断问题（一次一个）

是否确认走"自建轻量 Python 应用"路径？

- 推荐：是。技术栈草案：Python + 成熟 RSS 解析库 + SQLite + 调度器 + 本地 Web UI；AI 摘要支持本地模型或 OpenAI 兼容 API（密钥走环境变量，不落盘）
- 代价：核心功能全部自研，需先完成最小纵向闭环再扩展
- 备选：先试 Fluent Reader（最快可用，但缺摘要与去重）；或扩展其他候选（现代栈但缺口大）

## 要点

- 自建不是默认答案：是 40 个候选全部验证、缺口逐一确认后的结论。
- 证据等级诚实标注：E2 表示"工程证据充分但未本地运行"，不夸大为已验证。
- 决策后先定义纵向闭环再进入设计，避免"什么都做、什么都不通"。
