# 端到端案例：从开源评估到 Android 本地日记

> **v0.1 历史材料。** 这是高不确定性、跨边界的长任务，因此采用了重评、分阶段设计、纵向闭环和设备验收。v0.2 仅按任务风险采用这些措施，不把它们当作所有任务的固定流程。

这个脱敏案例来自一次真实的长任务，用来展示 Enough 如何处理约束变化、分阶段设计、纵向闭环和最终验收，也记录一次应当被回归测试捕获的“过早完成声明”。

## 输入

> 我想做一个情感生活记录 App，记录日期、活动、人物和心理活动，类似进阶版日记，并能一键导出全部内容。

## 第一次复用决策

初始平台尚未确定。搜索并核验多个开源候选后：

- Daily Nomie 的“事件—人物—活动—情绪—情境”模型最接近目标。
- Moodiary 和 StoryPad 已具备日记、附件、应用锁与备份能力。
- 候选只有工程与文档证据，尚未本地运行，证据为 E2。
- 初始推荐：使用并扩展 Daily Nomie。

这一阶段没有创建项目文件。

## 关键约束变化与重新评估

用户随后确定：

- 首发平台必须是原生 Android。
- 使用系统指纹、面容或锁屏凭据。
- 数据保存在本地，不依赖 Web 存储，不申请互联网权限。

这些约束改变了候选适用性。重新评估后的结论是：

- 推荐从“使用并扩展”改为“只借鉴”。
- 采用 Kotlin + Jetpack Compose 原生自建。
- 复用 Daily Nomie 的产品模型，借鉴其他候选的备份、照片和应用锁设计。

## 设计批准与里程碑

设计逐项确定人物、情绪、活动、照片、应用锁、提醒、七步心理梳理、每日总结和导出恢复。非目标包括账号、云同步、AI 分析和网络服务。

实施按可验收里程碑推进：

1. 系统身份验证 → 快速记录 → Room 持久化 → 首页读取。
2. 人物、活动、情绪、照片与七步梳理。
3. 时间线搜索、组合筛选、分页和本地洞察。
4. ZIP 导出、替换式恢复、回收站和提醒。
5. APK 构建、模拟器测试与发布前检查。

第一条纵向闭环通过后才扩大实现范围。

## 验收对账

| 验收项 | 状态 | 证据 | 缺口/下一步 |
| --- | --- | --- | --- |
| 编译、静态检查和单元测试 | 已验证 | 原生构建命令通过 | — |
| Android 设备测试 | 已验证 | API 36 模拟器上 5 项测试通过 | — |
| 导出—清空—恢复往返 | 已验证 | 数据、关联、梳理、总结与搜索索引恢复一致 | — |
| 可安装产物 | 已验证 | 带调试签名的 Debug APK 可安装 | 正式发布仍需签名 Release |
| Room 迁移自动化测试 | 未验证 | 测试依赖因网络问题未取得 | 保留显式迁移，待恢复自动化测试 |
| README 与项目规则沉淀 | 未完成 | 最终写入被权限网关拒绝 | 重新写入并核验落盘 |

因此，严格的 Enough 完成结论应是“核心产品已验证，交接与迁移测试部分完成”，而不是笼统的“全部完成”。

## 这个案例验证了什么

- 复用决策不是一次性结论；关键约束变化后必须重评。
- 一次只问一个阻断问题能控制方向，但非阻断选择应使用推荐默认值，避免审批疲劳。
- 最小纵向闭环能降低长任务全面铺开后的集成风险。
- 工具返回成功不等于文件实际落盘。
- 最终完成声明必须逐项对照已批准的验收标准。
